# Assistant-assisted setup

Read README.md first. Never request passwords or tokens in conversation or pass them into tools. Token entry belongs in a user-controlled interactive terminal, separate from MCP streams.

1. Explain that this is unofficial and experimental. Check macOS/Linux desktop, Python, uv, vault availability, and the client's ability to launch local stdio. Do not promise dot connectivity.
2. Clone the repo and run `uv sync --frozen`. Have the user sign in to Sleepme and obtain their developer token using the README instructions, then run `uv run --frozen chilipad-mcp setup` in their own terminal. Do not feed secrets through your terminal tool.
3. **Register the server before invoking MCP tools.** Use the absolute `.venv/bin/chilipad-mcp` executable with `serve` in the chosen client's configuration, then restart/reconnect. Test a real `list_devices` invocation. `uv run --frozen chilipad-mcp devices` is also available for read-only CLI discovery.
4. `list_devices` returns IDs, names, attachments, and discovery guidance. Zero devices means account/linking checks. Read each selected device with `get_device_status(device_id="RETURNED_ID")` before assigning sides; this verifies account membership and does not change or map a device. Explain its actual model, connectivity, and available readings.
5. For one device, ask the user to confirm a label and save the mapping. For two, offer identification only if the user needs it. More than two requires explicit selection of a bed/group first. Never infer left/right from ordering. Skip the temperature test if the user can already identify the controllers.
6. Optional identification: `identify_devices(action="begin", tests=[{"id":"SELECTED_ID_A","value":68,"unit":"F"},{"id":"SELECTED_ID_B","value":76,"unit":"F"}], confirmed=true)` requires agreement to the exact values and devices. These numbers are illustrative, not comfort defaults. Include `on` only if power changes were explicitly agreed. No maximum modes. Stop if either outcome fails; explain pending recovery.
7. Ask which controller belongs to which side. Read back aliases, IDs, optional group and viewpoint; call `save_device_mapping(rows=[...], confirmed=true)` only after confirmation. This **replaces the full mapping**: include every existing assignment the user wants to retain. `position`, e.g. “left while lying in bed,” is optional metadata.
8. If identification ran, `identify_devices(action="finish")` restores by default and verifies original settings through reads. Keeping test settings requires `keep=true, confirmed=true`. If recovery remains pending, explain each controller's result. For cancel/interruption use `recover` or `cancel`; never overwrite possible manual temperature or power changes without fresh agreement (`force=true, confirmed=true`). Recovery is explicit on restart; the server reports it and blocks conflicting writes until resolved.
9. Confirm a read through the saved alias. Offer only requested routines. Collect target, action time, timezone, recurrence or exact date, temperature, power choice, and allowed catch-up window. Explain inbox-only notifications and 12-hour command suppression. Run `uv run --frozen chilipad-mcp notification-test`, inspect `inbox`, then save and enable only agreed routines. Verify one foreground test occurrence, stop that runner with Ctrl-C, and follow the background-service guide. Validate an actual background run before declaring it operational.

Local mappings are convenience labels for one OS user, not an authorization boundary. Use a separate OS account for another person; avoid multiple active profiles using the same Sleepme account because budgets would be split.

No relative-temperature tool ships in v0.1. Read the saved target, show the computed value and unit, validate representability, and ask for clarification if a maximum mode or ambiguous side is involved. Never round or guess. Use independent calls for explicit multi-side requests and report partial failures.
